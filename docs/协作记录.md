## 一、协作目标

对应《开源文化运动》期末考核要求第（4）条：

> 邀请同学进行 issue 讨论，star、watch 等

拆解为四个可验证动作：

| 动作 | 平台位置 | 验收证据 |
|------|---------|---------|
| 邀请同学 | 仓库 → Settings → Collaborators，或直接分享仓库链接 | 同学 GitHub 账号出现在协作者列表 / 讨论串 |
| Issue 讨论 | 仓库 → Issues → New issue | 至少 3 个 Issue，每个有同学回复 |
| Star | 仓库右上角 ⭐ Star | 仓库 Star 数 ≥ 同学人数 |
| Watch | 仓库右上角 👁 Watch → All Activity | 同学的 Watch 状态 |

## 二、邀请与协作流程

### 2.1 邀请同学

1. 将仓库地址发给同学：`https://github.com/MarkSoul7/mdag_29`
2. 需要对方参与代码修改时：**Settings → Collaborators → Add people**，输入对方
   GitHub 用户名，选择 `Write` 权限；
3. 仅参与讨论时无需添加协作者——公开仓库的 Issue 对所有人开放；
4. 请同学点击 **Star** 与 **Watch → All Activity**，以便接收 Issue 通知。

> 安全提示：不要给不熟悉的账号 `Admin` 权限；作业结束后可在 Collaborators 中移除。

### 2.2 发起 Issue 讨论

仓库已配置三种 Issue 模板（Bug / 功能建议 / 提问），路径：
`.github/ISSUE_TEMPLATE/`。建议按下面三个议题发起讨论，正文可直接使用
[Issue 讨论提纲](Issue讨论提纲.md)。

### 2.3 评审与合并

同学提出修改建议时：

1. 请对方 Fork 仓库并从 `main` 切出 `docs/` 或 `fix/` 分支；
2. 提交 PR，填写模板；
3. 维护者在 PR 中回复、请求修改，CI 通过后合并；
4. 在 Issue 中回复“已在 #PR 编号 解决”，并关闭 Issue。

## 五、协作规范（与 CONTRIBUTING 一致）

1. 一个 Issue 只讨论一个问题，标题写清楚“是什么”而不是“有问题”；
2. 回复时引用具体代码位置或命令输出，避免“我觉得”；
3. 结论必须落到“采纳 / 不采纳 + 理由”，不接受无结论的长讨论；
4. 代码类建议必须附测试或复现步骤；
5. 合并前 CI 必须通过，评审意见必须回复（同意或说明原因）。
