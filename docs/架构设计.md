# 架构设计说明

本文说明 mdag_29 的分层结构、对象编码规则、导入与解析流程，以及关键设计权衡，
用于回答“为什么这样实现”以及“后续如何扩展”。

---

## 一、设计目标与非目标

### 1.1 目标

1. **最小可解释**：核心概念（CID、HashLink、Merkle DAG、Resolver）都能在几百行代码内
   找到唯一对应实现，适合教学与代码审查。
2. **字节级可复现**：同一份内容在任何机器、任何时间导入，CID 必须一致。
3. **接口可替换**：存储后端通过 `Store` 接口抽象，便于替换为数据库、对象存储或网络后端。
4. **错误可诊断**：错误信息包含具体路径、CID 与失败原因，而不是笼统的 “failed”。

### 1.2 非目标（明确不做）

| 非目标 | 原因 |
|--------|------|
| P2P 网络与内容寻址网络 | 属于 IPFS 的领域，超出课程项目边界 |
| 高并发与性能优化 | 教学场景数据量小，优先正确性与可读性 |
| 垃圾回收 / 快照管理 | 需要引用计数或根集合，留作后续路线图 |
| 权限与多租户 | 单机 CLI 工具，无此需求 |
| 图形界面 | CLI 足以演示全部能力 |

## 二、总体分层

```text
┌─────────────────────────────────────────────┐
│ cmd/mdag (CLI)                              │
│   add / resolve / cat / ls / --mem          │
└───────────────┬─────────────────────────────┘
                │
     ┌──────────┴───────────┐
     ▼                      ▼
┌─────────────┐      ┌─────────────┐
│ importer    │      │ resolver    │
│ 文件/目录→对象 │      │ 路径→对象    │
└──────┬──────┘      └──────┬──────┘
       │                    │
       └────────┬───────────┘
                ▼
        ┌───────────────┐
        │ store.Store   │  PutObject / GetObject
        └───┬───────┬───┘
            ▼       ▼
     ┌──────────┐ ┌──────────┐
     │ FileStore│ │MemoryStore│
     │ ./data   │ │ map[cid]  │
     └──────────┘ └──────────┘
                │
                ▼
        ┌───────────────┐
        │ object.Object │  Blob / Tree / List + CID
        └───────────────┘
```

依赖方向单一：上层依赖下层，`object` 不依赖任何其他内部包，`store` 只依赖
`object`，因此可以独立测试与替换。

## 三、对象编码规则

### 3.1 三种对象

| 类型 | 字段 | 语义 |
|------|------|------|
| `blob` | `Data` | 文件原始字节 |
| `tree` | `Links` | 目录项：名称 + 子 CID + 大小 |
| `list` | `Links` | 大文件分块：有序的块 CID + 块大小 |

### 3.2 序列化与 CID

```go
func ComputeCID(obj Object) (string, error) {
    data, err := json.Marshal(obj)
    if err != nil { return "", fmt.Errorf("serialise object: %w", err) }
    sum := sha256.Sum256(data)
    return hex.EncodeToString(sum[:]), nil
}
```

确定性来自三点：

1. **字段顺序固定**：Go 结构体字段声明顺序即 JSON 顺序（type → data → links）；
2. **`omitempty` 规则固定**：空的 `Data`、`Links` 不会出现在 JSON 中；
3. **`[]byte` 编码固定**：标准库使用 base64，不依赖本地编码。

> 注意：如果未来增删字段，必须同步升级对象格式版本，否则同一份内容会得到不同 CID。
> 这也是路线图中“对象格式版本号”存在的原因。

### 3.3 为什么选 SHA-256

- 标准库自带，零依赖；
- 256 位抗碰撞性足够，且与区块链课程中的哈希概念一致；
- 十六进制 64 字符，便于命令行复制与比较。
- 代价是比 BLAKE3 慢，但本项目瓶颈在磁盘 I/O，不在哈希。

## 四、导入流程

`importer.AddPath(path, store)`：

1. `os.Stat` 判断文件或目录；
2. 文件 → 读取全部字节 → 构造 Blob → `store.PutObject` → 返回 CID；
3. 目录 → `os.ReadDir` → **按名称排序** → 递归导入每个子项 → 构造 Tree →
   `PutObject` → 返回 CID。

排序是确定性的关键：文件系统的目录顺序不保证稳定（不同 OS、不同次读取都可能不同），
若不排序，同样的目录可能得到不同的根 CID。排序后，导入结果与文件系统枚举顺序无关。

```go
sort.Slice(entries, func(i, j int) bool {
    return entries[i].Name() < entries[j].Name()
})
```

### 4.1 去重

`PutObject` 先计算 CID：若 `<cid>.json` 已存在则直接返回，不重复写盘；相同内容的
两个文件在存储层只占一份空间。这是内容寻址系统的天然特性。

### 4.2 大文件分块（List）

`AddPathWithChunkSize` 把大于 `chunkSize` 的文件切成多个 Blob，再用 List 按顺序
引用。小块可以被不同文件共享，适合增量同步与断点续传。当前 CLI 尚未暴露该参数，
仅通过测试与库调用使用，属于路线图中的待办项。

## 五、CID 传播与去重

以 `testdata/demo` 为例，只修改 `docs/report.txt`：

```text
report.txt 内容变化
   └─ report.txt Blob CID 变化 (9f9b... → 新值)
        └─ docs Tree 的 Link 中 report.txt 的 CID 变化
             └─ docs Tree CID 变化 (1a13... → 新值)
                  └─ 根 Tree 的 Link 中 docs 的 CID 变化
                       └─ 根 CID 变化 (ae03... → 新值)

notes.txt 未变化 → 其 CID 不变 (04a6...)
```

这带来两个性质：

- **完整性校验**：只要根 CID 可信，就能递归校验整棵树的每个字节；
- **局部影响**：修改一个文件不会“污染”无关子树，便于增量传输与缓存。

`mdag_test.go` 中的 `TestModifyFile_ChangesCID` 对上述传播链做了断言。

## 六、路径解析

`resolver.Resolve(rootCID, path, store)`：

```text
1. 规范化路径：去掉首尾 "/"，按 "/" 拆分
2. 若路径为空：读取根对象，返回 {rootCID, 根类型}
3. 逐段循环：
   a. 读取当前 CID 对应对象
   b. 若不是 tree → 报错 "is a X, not a tree"
   c. 在 Links 中按 name 查找
   d. 找不到 → 报错 "name X not found in tree <cid>"
   e. 命中 → 更新当前 CID
4. 最后一段命中后，读取目标对象并返回其类型
```

复杂度为 O(深度 × 每层子项数)，与文件内容大小无关。因为 Tree 的 Links 是线性数组，
当前实现使用线性查找；若目录项达到数千级，可改为排序后二分或增加索引，但这会改变
对象编码，进而改变 CID，因此暂不实施。

### 6.1 类型安全

- `cat` 只接受 Blob（或 List 拼接），对 Tree 报错；
- `ls` 只接受 Tree，对 Blob 报错；
- 解析中间节点必须是 Tree，否则报“无法下钻”。

## 七、存储实现

### 7.1 FileStore

- 目录：`./data`（相对当前工作目录，可通过 `NewFileStore` 指定）；
- 文件名：`<cid>.json`；
- 写入：先 `Stat` 判重，再 `os.WriteFile`（0644）；
- 读取：`os.ReadFile` + `json.Unmarshal`。

**已知限制**：写入不是原子操作（未使用临时文件 + rename），进程在写入中途崩溃可能
留下半个 JSON。生产级实现应改为“写临时文件 → fsync → rename”。当前版本通过
“内容寻址 + 可重新导入”降低影响。

### 7.2 MemoryStore

`map[string]object.Object`，用于单元测试与 `--mem` 演示。Put 幂等，Get 未命中返回
`object <cid>: not found`。

### 7.3 接口契约

```go
type Store interface {
    PutObject(obj object.Object) (string, error)
    GetObject(cid string) (object.Object, error)
}
```

任何实现都必须满足：Put 幂等、相同对象返回相同 CID、Get 只按 CID 读取。新增后端
（SQLite、S3、HTTP）只需实现这两个方法。

## 八、错误处理约定

- 使用 `fmt.Errorf("...: %w", err)` 包装底层错误，保留错误链；
- 错误信息包含**上下文**（路径、CID、操作），便于定位；
- CLI 将错误写入 stderr 并以退出码 1 结束，成功退出码 0；
- 不 panic（`MustComputeCID` 仅用于已知不会失败的对象构造场景）。

## 九、设计权衡

| 决策 | 选择 | 放弃的方案 | 理由 |
|------|------|-----------|------|
| 序列化 | JSON | protobuf / CBOR | 可读、标准库支持、便于教学 |
| 哈希 | SHA-256 | BLAKE3 / SHA-1 | 标准库、安全、与课程概念一致 |
| 存储布局 | 每对象一个文件 | 单文件数据库 | 直观、可用 ls 观察、易调试 |
| 文件内容编码 | base64（json []byte） | 原始字节拼 JSON | 标准库行为，避免手写转义 |
| 分块 | 定长块 List | Rabin 滚动哈希 | 实现简单，先讲清原理 |
| 并发 | 无锁 | 文件锁 / 单写者 | CLI 单进程场景，先保持简单 |

## 十、扩展点

1. **新存储后端**：实现 `Store` 两个方法即可（如 SQLite、S3）。
2. **对象格式版本**：在 Object 中增加 `version` 字段，CID 计算纳入版本号。
3. **GC**：维护根集合，从根出发标记可达对象，删除不可达的 `<cid>.json`。
4. **HTTP 网关**：把 `Resolve` + `ReadFile` 暴露为只读接口。
5. **CLI 分块**：增加 `add --chunk-size`，把 `AddPathWithChunkSize` 接入。

---

## 十一、已知限制

- 不处理符号链接（`os.Stat` 会跟随链接）；
- 导入大文件时一次性读入内存；
- FileStore 无并发写保护；
- 数据目录相对工作目录，换目录运行会“看不到”之前的对象；
- 无对象格式版本号，字段变更会破坏兼容性。

这些限制在 [README 路线图](../README.md#九路线图) 中对应到具体待办项。
