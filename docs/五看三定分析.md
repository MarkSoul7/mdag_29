# mdag_29 项目“五看三定”战略分析

> 分析对象：开源项目 `mdag_29`（简化版 Merkle DAG 文件存储与路径解析系统）  
> 分析方法：华为“五看三定”战略规划框架  
> 分析人：杨琦航（2023131029）  
> 日期：2026-11-09

---

## 摘要

mdag_29 是一个核心约 600 行、零第三方依赖的 Go 项目，用 Blob / Tree / List 三种对象和
SHA-256 内容标识（CID）实现了一个可运行、可验证的微型内容寻址文件系统。

用“五看三定”审视后，本项目的结论是：

- **行业趋势**支持“内容寻址”从存储技术上升为数据可信基础设施，但该赛道已有 IPFS、
  Git 等强势玩家；
- **市场**的真实缺口不在“再做一个 IPFS”，而在“能讲清楚原理、能跑起来、能改得动的
  教学与原型内核”；
- **竞争**中我们无法在性能、网络、生态上取胜，只能选择“可解释性 + 可验证性”作为
  差异化；
- **自己**的优势是边界清晰、代码量小、测试完整，劣势是单人维护、无网络能力、无社区；
- **机会**集中在课程复用、中文教学开源、轻量嵌入式组件三条路径。

据此确定：**战略控制点 = “可解释 + 可验证”的教学级 Merkle DAG 内核**；
目标分课程、开源、技术三层；策略是“教学优先、文档即产品、小步提交、社区冷启动、
克制范围”。

## 一、方法说明

华为“五看三定”是一套把“战略思考”落到“可执行规划”的工具：

| 阶段 | 要素 | 回答的问题 |
|------|------|-----------|
| 五看 | 看行业/趋势 | 外部环境朝哪里走？ |
| | 看市场/客户 | 谁有需求？需求是否真实？ |
| | 看竞争 | 对手是谁？我们凭什么赢？ |
| | 看自己 | 我们有什么？缺什么？ |
| | 看机会 | 哪些机会值得投入？ |
| 三定 | 定战略控制点 | 什么优势难以被复制、可长期积累？ |
| | 定目标 | 做到什么程度算成功？ |
| | 定策略 | 用什么路径和资源达成？ |

对一个课程开源项目而言，“五看三定”的价值不是写一份宏大战略，而是**逼自己回答
“不做什么”**——个人项目的失败通常不是做得太少，而是范围失控。

## 二、五看

### 2.1 看行业/趋势

**（1）数据要素化与可信数据基础设施。** 数据要成为可流通的要素，前提是可确权、
可追溯、可校验。内容寻址（Content Addressing）用“内容哈希”而不是“存储位置”标识
数据，天然满足“同样内容得到同样标识、任何篡改都会改变标识”，是数据血缘、版本管理、
去重备份的底层机制。

**（2）AI 数据管道对“数据集版本化”的需求上升。** 训练数据需要可复现：同一份数据集
必须能定位到确定的字节集合。DVC、LakeFS、IPFS 等工具都在用内容哈希解决“这份数据
到底是哪一版”的问题。Merkle DAG 正是把“目录 → 文件 → 分块”组织成可校验整体结构
的经典方法。

**（3）Web3 与区块链的工程教育需求。** Merkle 树/Merkle DAG 是区块链轻客户端证明、
交易完整性校验的基础结构。高校区块链专业需要“能跑、能改、能讲清楚”的教学实现，
而不是只讲概念的 PPT。

**（4）开源与国产化工具链。** Go 语言在云原生领域生态成熟，标准库自带 SHA-256、
JSON、文件系统操作，适合做零依赖教学项目；中文文档的优质教学项目仍然稀缺。

**趋势判断**：内容寻址正从“存储优化技术”变成“数据治理基础设施”的一部分；但通用
基础设施层已经被成熟项目占据。对本项目而言，顺势的方向不是“做基础设施”，而是
“做理解基础设施的最小内核”。

### 2.2 看市场/客户

把潜在使用者分成四层，分别看需求强度与付费/参与意愿：

| 客户群 | 真实痛点 | 需求强度 | 参与意愿 | 本项目的回应 |
|--------|---------|---------|---------|-------------|
| 高校课程（区块链/分布式/数据库） | 教材偏理论，缺少可运行、可修改的完整样例 | 高 | 中（教师愿意复用） | 提供 600 行、10 个测试、中文文档的教学内核 |
| 自学开发者 / 转行者 | 教程只讲概念，代码跑不起来 | 中高 | 高（star、issue） | 5 分钟跑通，命令输出与原理一一对应 |
| 小型团队内部工具 | 需要轻量内容寻址层做构建缓存、去重备份 | 中 | 低（更倾向成熟方案） | 可复用的 Go 包与清晰接口 |
| 开源贡献者 | 想找“小而完整”的项目练手 | 中 | 高 | 明确的 good first issue 与贡献指南 |

**关键判断**：

1. 教学市场“小、稳、付费意愿低”，但**传播性强**——一个老师用得好，会带来下一届
   学生与同行复用。
2. 工具市场“大、竞争激烈、信任门槛高”，个人项目短期无法进入。
3. 因此客户策略应是：**以教学客户为切入点，以自学开发者为传播放大器，以小型团队
   为长期变现/复用可能**，而不是一上来做通用工具。

### 2.3 看竞争

| 竞争者 | 定位 | 优势 | 劣势（相对本项目） |
|--------|------|------|------------------|
| **Git** | 版本控制 + 内容寻址对象库 | 工业级、生态巨大、Merkle DAG 经典实现 | 对象模型与工作流复杂，不适合作为“第一次理解 Merkle DAG”的读物 |
| **IPFS** | P2P 内容寻址网络 | 完整协议、全球网络、活跃社区 | 系统庞大、概念多（DHT、Bitswap、libp2p），学习曲线陡 |
| **DVC** | ML 数据/模型版本管理 | 与 Git/Python 生态结合好 | 面向 ML 工作流，核心不是讲清 Merkle DAG |
| **rsync / 备份工具** | 文件同步与备份 | 成熟、快 | 基于路径而非内容哈希，无全局去重与可验证结构 |
| **教学玩具项目** | 课程作业 | 简单 | 多数缺测试、缺文档、边界不清 |

**竞争结论**：

- 在“功能完整性”上我们必输，也不应参赛；
- 在“**单位时间理解成本**”上我们有优势：一个文件一个概念，命令输出直接对应数据结构；
- 差异化定位：**不是更快的 IPFS，而是更清楚的 Merkle DAG 教材 + 可执行参考实现**。

需要诚实承认的劣势：无网络、无 GC、无并发优化、单人维护、无社区背书。这些劣势决定
我们不能承诺“生产可用”。

### 2.4 看自己

**资源盘点**：

| 维度 | 现状 |
|------|------|
| 人力 | 1 人（课程周期内开发） |
| 技术栈 | Go 1.24，标准库，零第三方依赖 |
| 代码规模 | 约 600 行（含测试约 900 行） |
| 质量保障 | 10 个自动化测试，全部通过；GitHub Actions CI |
| 文档 | README + 架构设计 + 分支管理 + 协作记录 + 五看三定 + 作业对照 + Issue 提纲 |
| 社区 | 刚建立仓库，0 star（截至本文撰写） |

**能力评估**：

- 强项：数据结构与哈希原理理解、Go 编码、文档写作、把复杂概念拆解成可运行示例；
- 弱项：分布式系统、性能工程、开源社区运营、跨平台打包；
- 机会：课程与同学资源可用于首批用户与 issue 讨论；
- 威胁：时间碎片化、范围蔓延、后续维护动力不足。

**SWOT**：

| | 有利 | 不利 |
|---|------|------|
| **内部** | S1 代码小且完整；S2 测试与 CI；S3 中文文档；S4 零依赖易构建 | W1 单人维护；W2 无网络/GC；W3 无性能优化；W4 无社区影响力 |
| **外部** | O1 教学内容缺口；O2 AI 数据版本化趋势；O3 课程复用；O4 Go 生态 | T1 IPFS/Git 强势；T2 教学项目同质化；T3 维护者时间不足 |

### 2.5 看机会

把机会按“吸引力 × 可行性”筛选（高/中/低为定性判断）：

| 机会点 | 吸引力 | 可行性 | 判断 |
|--------|--------|--------|------|
| A. 课程实验脚手架（教师/学生复用） | 高 | 高 | **优先做**：现有代码与文档已具备条件 |
| B. 中文 Merkle DAG 教学开源项目 | 高 | 中高 | **优先做**：差异化明确，但需持续写作 |
| C. 轻量内容寻址 Go 库（构建缓存/去重备份） | 中 | 中 | 观察：需要 API 稳定与性能验证 |
| D. 只读 HTTP 网关 / 可视化 | 中 | 中 | 二期：能显著提升演示效果 |
| E. P2P 网络层 | 低 | 低 | **不做**：与 IPFS 正面竞争，资源不匹配 |
| F. 商业化/SaaS | 低 | 低 | **不做**：偏离课程目标 |

**机会结论**：短期把 A、B 做透（教学内核 + 文档），中期用 D 提升演示与传播，C 作为
技术演进的备选；坚决放弃 E、F。

## 三、三定

### 3.1 定战略控制点

**定义**：战略控制点是“难以被复制、能持续积累、能支撑长期竞争”的关键优势。

**候选评估**：

| 候选控制点 | 可复制性 | 可积累性 | 结论 |
|-----------|---------|---------|------|
| 性能（更快哈希/并发） | 高（易被超越） | 低 | 放弃 |
| 网络规模（节点数） | 极高门槛 | 需资本 | 放弃 |
| 功能数量 | 高 | 低 | 放弃 |
| **可解释性**（代码-文档-输出一一对应） | 低（需长期打磨） | 高 | **选定** |
| **可验证性**（测试覆盖关键不变量） | 中 | 高 | **选定** |

**最终控制点**：

> **“可解释 + 可验证”的教学级 Merkle DAG 内核。**

拆解为三条可执行的护城河：

1. **可解释**：README 的每个概念都能指向具体文件与函数；每条命令的输入输出都能对应
   到对象结构；没有“黑盒”。
2. **可验证**：关键不变量（同内容同 CID、改文件根 CID 变、无关文件 CID 不变、错误路径
   可诊断）都有测试断言；CI 每次 push 自动执行。
3. **可复现**：固定测试数据、固定序列化规则、固定行尾策略，任何人克隆后得到相同 CID。

**明确不做的三件事**（战略克制）：

- 不做 P2P 网络（不与 IPFS 竞争）；
- 不做性能军备竞赛（不与 Git 比速度）；
- 不做 GUI（不分散文档与内核精力）。

### 3.2 定目标

目标遵循 SMART 原则，分三层，避免“一句话口号”：

| 层级 | 目标 | 衡量指标 | 时间 | 现状 |
|------|------|---------|------|------|
| 课程目标 | 通过期末考核，形成可展示的开源项目 | 5 项作业要求全部有仓库证据；10/10 测试通过 | 2026-11 | 基本达成 |
| 开源目标 | 建立可被外部使用的项目主页 | README 完整；≥3 个 issue 讨论；≥10 star；≥2 位同学 star/watch | 1 个学期 | 进行中 |
| 技术目标 | 补齐工程化短板 | CLI 支持分块；新增 `fsck`；测试覆盖率 ≥ 80% | 3 个月 | 未开始 |
| 生态目标 | 被至少 1 门课程或 1 个项目复用 | 复用案例 1 个；外部 PR ≥ 3 | 1 年 | 未开始 |

**目标取舍**：课程目标是“必须达成”，开源目标是“努力达成”，技术与生态目标是“方向
性承诺”。不把未完成的目标包装成已完成。

### 3.3 定策略

| 策略 | 具体动作 | 支撑的目标 | 风险与对策 |
|------|---------|-----------|-----------|
| **教学优先** | 文档按“5 分钟跑通 → 原理 → 代码 → 扩展”组织；每个概念配可执行示例 | 课程、开源 | 文档过长→分层：README 概览，docs 深入 |
| **文档即产品** | README、架构、五看三定、分支管理、协作记录成套；图文化 | 开源、生态 | 维护成本→模板化、定期校对 |
| **小步提交 + 分支模型** | main 保护；feature/docs 分支；Conventional Commits；PR 评审 | 技术、课程 | 流程过重→个人项目用简化 Git Flow |
| **社区冷启动** | Issue 模板、good first issue、邀请同学讨论、课堂演示 | 开源 | 无人参与→先找 3 位同学做种子用户 |
| **技术演进克制** | 先稳定 CID 与对象格式，再扩展 Store；网络层明确不做 | 技术 | 范围蔓延→以“控制点”为准绳拒绝需求 |
| **质量门禁** | CI 执行 gofmt、go vet、全部测试；合并前必须绿 | 技术、开源 | CI 失败→本地 pre-push 自检 |

**策略与目标的映射**：课程目标靠“教学优先 + 质量门禁”；开源目标靠“文档即产品 +
社区冷启动”；技术目标靠“小步提交 + 技术演进克制”；生态目标靠前两者累积的口碑。

## 四、结论与行动清单

### 4.1 一句话战略

> 用最小的代码把 Merkle DAG 讲清楚，用测试把“讲清楚”变成“可验证”，再把这份可验证的
> 理解做成可复用的教学资产——不与基础设施巨头比规模，只比“读懂它需要多久”。

### 4.2 30 / 60 / 90 天行动

| 时间 | 行动 | 验收标准 |
|------|------|---------|
| 0–30 天 | 完成仓库建设与作业要求；邀请 3 位同学 star/watch 并提 issue | 5 项要求有证据；3 条 issue 有回复 |
| 31–60 天 | 增加 `mdag fsck` 与 `add --chunk-size`；补充测试 | 新功能有测试；覆盖率提升 |
| 61–90 天 | 写一篇“从零实现 Merkle DAG”教程；在课程/社团做一次分享 | 教程发布；至少 1 次外部反馈 |

### 4.3 复盘机制

- 每月对照目标表更新“现状”列；
- 每季度重做一次“五看”，重点看竞争格局与自身资源变化；
- 若连续两个季度开源目标无进展，则收缩范围，保住“教学内核”这一条主线。

## 附：分析边界与说明

1. 本文是**课程项目的战略练习**，不是商业计划书；市场判断为定性分析，未引用付费
   调研数据。
2. “五看三定”中的“看行业/市场”基于公开的行业常识与技术文档（Git、IPFS、DVC 的
   公开设计），未虚构统计数据。
3. 目标表中的数字是**承诺性目标**，不是既成事实；现状列如实标注“进行中/未开始”。
4. 战略控制点的选择服从个人项目约束：资源有限时，选择“可积累、可复制成本低”的
   方向，而不是“看起来更大”的方向。
