# 分支管理与冲突处理记录

本文记录 mdag_29 仓库实际使用的分支模型、真实的合并历史，以及一次真实的合并冲突
从发生到解决的完整过程。所有提交哈希均可通过 `git log --graph --all` 复核。

---

## 一、为什么需要分支管理

即使是一个人开发，分支也有三个实际作用：

1. **隔离风险**：文档、CI、功能互不干扰，`main` 始终可构建；
2. **保留决策上下文**：一个分支对应一个主题，合并提交（merge commit）把“为什么改”
   固化在历史里；
3. **模拟协作**：分支 + PR + 评审是开源协作的最小单元，课程项目也应走一遍完整流程。

---

## 二、分支模型

采用简化版 Git Flow，只有两类长期/短期分支：

```text
main ────●────●────●────●──────────────●────────●──────►
          \    \    \    \            /        /
           \    \    \    feature/…  /        /
            \    \    docs/…        /        /
             \    feature/ci-workflow       /
              \                            /
               └── feature/quickstart-* ──┘（并行修改同一文件 → 冲突）
```

| 分支类型 | 命名 | 生命周期 | 合并方式 |
|---------|------|---------|---------|
| 稳定分支 | `main` | 长期 | 只接受 PR / 合并 |
| 功能分支 | `feature/<name>` | 短期 | `--no-ff` 合入 main |
| 文档分支 | `docs/<name>` | 短期 | `--no-ff` 合入 main |
| 修复分支 | `fix/<name>` | 短期 | `--no-ff` 合入 main |

**规则**：

1. 任何改动都从最新 `main` 切出分支，不在 `main` 上直接提交；
2. 合并统一使用 `git merge --no-ff`，保留分支拓扑，便于回溯；
3. 合并前本地执行 `gofmt -l .`、`go vet ./...`、`go test ./...`；
4. 合并后 `main` 必须保持可构建、测试通过。

> 本仓库为了便于老师与同学复核，**保留已合并的分支**而不删除；实际项目中合并后
> 通常执行 `git branch -d <name>` 与 `git push origin --delete <name>`。

### 3.1 典型合并命令

```bash
# 从 main 切出功能分支
git checkout main
git pull --ff-only
git checkout -b feature/fsck

# 开发并提交
git add .
git commit -m "feat: 增加 fsck 子命令"

# 回到 main 合并（保留分支历史）
git checkout main
git merge --no-ff feature/fsck -m "merge: 合并 feature/fsck"
```

使用 `--no-ff` 而不是快进合并，是为了在历史上留下“这里合并过一个分支”的显式记录；
快进合并会让分支消失得无影无踪，事后无法判断某组改动属于哪个主题。

## 四、冲突案例复盘

### 4.1 背景

README 的“2.2 获取与构建”一节需要补充平台说明。两位贡献者（模拟并行开发）分别从
同一个 `main` 切出分支：

- `feature/quickstart-windows`：在构建命令后插入“#### Windows 说明”；
- `feature/quickstart-linux`：在**同一位置**插入“#### Linux / macOS 说明”。

两个分支都修改了 README 的同一区域，且插入点相同，因此无法自动合并。

### 4.2 复现步骤

```bash
git checkout main
git checkout -b feature/quickstart-windows
# 编辑 README，在“Windows 下建议把产物命名为 mdag.exe”之前插入 Windows 说明
git add README.md
git commit -m "docs: 补充 Windows 平台构建与 Git Bash 路径说明"

git checkout main
git checkout -b feature/quickstart-linux
# 在同一位置插入 Linux / macOS 说明
git add README.md
git commit -m "docs: 补充 Linux 与 macOS 的安装说明"

git checkout main
git merge --no-ff feature/quickstart-windows -m "merge: 合并 feature/quickstart-windows"
git merge --no-ff feature/quickstart-linux  -m "merge: 合并 feature/quickstart-linux"
```

### 4.3 冲突现场

```text
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

`git status` 显示：

```text
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   README.md
```

README.md 中的冲突标记（`git diff` 同样可见）：

```text
<<<<<<< HEAD
#### Windows 说明

在 PowerShell 或 CMD 中直接使用上面的命令即可。若在 Git Bash 中执行 resolve、cat、
ls 等子命令，请先运行 export MSYS_NO_PATHCONV=1，否则 /docs 会被 MSYS 改写成
Windows 绝对路径，导致 "name C: not found in tree" 错误。
=======
#### Linux / macOS 说明

产物可直接运行，也可以安装到 PATH：

chmod +x mdag
sudo mv mdag /usr/local/bin/
>>>>>>> feature/quickstart-linux
Windows 下建议把产物命名为 mdag.exe：
```

- `<<<<<<< HEAD` 到 `=======`：当前分支（main，已含 Windows 分支）的内容；
- `=======` 到 `>>>>>>> feature/quickstart-linux`：被合并分支的内容；
- 两者都是“新增平台说明”，**没有语义冲突**，只是文本位置重叠。

### 4.4 解决过程

**第一步：判断冲突性质。** 打开冲突文件，确认两边不是对同一句话给出不同事实，而是
两块可以共存的内容。若两边是互斥修改（例如一边写“端口 8080”、另一边写“端口 9090”），
则必须先确认哪个正确，不能简单保留两边。

**第二步：手工编辑，保留双方内容并确定顺序。** 删除 `<<<<<<<`、`=======`、
`>>>>>>>` 三行标记，按“Windows → Linux/macOS → 原句”的顺序合并：

```markdown
#### Windows 说明

在 PowerShell 或 CMD 中直接使用上面的命令即可。若在 Git Bash 中执行 resolve、cat、
ls 等子命令，请先运行 export MSYS_NO_PATHCONV=1，否则 /docs 会被 MSYS 改写成
Windows 绝对路径，导致 "name C: not found in tree" 错误。

#### Linux / macOS 说明

产物可直接运行，也可以安装到 PATH：

chmod +x mdag
sudo mv mdag /usr/local/bin/

Windows 下建议把产物命名为 mdag.exe：
```

顺序理由：README 的主要读者在 Windows 上按“获取与构建”操作，Windows 说明紧跟构建
命令更顺手；Linux 说明作为补充放在其后。

**第三步：确认没有残留标记并提交。**

```bash
grep -rn '<<<<<<<\|=======\|>>>>>>>' README.md   # 应无输出
git add README.md
git commit -m "merge: 合并 feature/quickstart-linux 并解决 README 快速开始的冲突"
```

提交后历史中出现一个合并节点 `b845b2f`，它有两个父提交：
`a834dc5`（合并 Windows 后的 main）与 `bbe229c`（Linux 分支）。

```bash
git show --no-patch --format='%h %p %s' b845b2f
# b845b2f a834dc5 bbe229c merge: 合并 feature/quickstart-linux 并解决 README 快速开始的冲突
```

### 4.5 验证

解决冲突后重新执行完整验证，确保合并没有引入回归：

```bash
gofmt -l .                 # 无输出
go vet ./...               # 无输出
go test -count=1 ./...     # ok mdag
go build -o mdag.exe ./cmd/mdag
```

README 渲染检查：平台说明位于构建命令之后，代码块闭合，链接可跳转。

## 五、经验总结

1. **小步、短分支**：分支存活时间越长，冲突概率越高。一个分支只做一件事。
2. **先拉后切**：切分支前 `git pull --ff-only`，避免基于过期 main 开发。
3. **冲突不是错误**：冲突是 Git 在提醒“这段文本有两个来源，需要人来判断”。
4. **保留双方 ≠ 正确**：文本冲突可以共存，语义冲突必须查证事实后再决定。
5. **解决后必须验证**：至少跑格式化、静态检查、测试与构建，避免“合并成功但跑不起来”。
6. **用 `--no-ff` 保留上下文**：合并提交记录了“为什么这两组改动同时存在”。
